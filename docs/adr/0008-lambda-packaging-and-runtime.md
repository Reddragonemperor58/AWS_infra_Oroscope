# ADR 0008: Lambda Packaging and Runtime Compatibility

## Context
AWS Lambda currently supports a maximum Python runtime of 3.13, while local development environments may run newer versions (e.g., Python 3.14). Furthermore, dependencies like `pydantic` rely on compiled C/Rust extensions. A naive `pip freeze` and zip operation results in bloated deployment packages and runtime crashes due to glibc/bytecode mismatches.

## Decisions
1. **Targeted Binary Resolution:** We require `pip install --platform manylinux2014_x86_64 --implementation cp --python-version 3.13 --only-binary=:all:` during packaging. This forces pip to pull AWS-compatible binaries and strictly prevents silent fallbacks to local source compilation.
2. **Deterministic Dependency Bundling:** Even though AWS Lambda provides `boto3` natively in its execution environment, we explicitly bundle it in `requirements.txt`. Because `sqlalchemy-aurora-data-api` relies heavily on `boto3`, bundling guarantees our Lambda runs the exact version we tested locally, protecting the app from underlying AWS environment updates.
3. **Strict Dependency Isolation:** Local ASGI servers (`uvicorn`), migration tools (`alembic`), and testing suites (`pytest`) are strictly isolated to `requirements-dev.txt` to prevent dead-weight deployments.
4. **Bytecode Exclusion:** The `zip` command must use `-x "*/__pycache__/*" -x "*.pyc"` to strip all locally generated bytecode, forcing Lambda to compile native 3.13 bytecode on the first cold start.

## Consequences
* The deployment zip is marginally larger due to the deterministic `boto3` inclusion.
* We completely avoid cross-platform compiled extension crashes in production.
* Lambda cold starts are optimized by stripping unnecessary dev tooling and test directories.
